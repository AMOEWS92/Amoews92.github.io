Software Design and Engineering Enhancement Narrative

Travlr Getaways is a full-stack web application built using the MEAN stack: MongoDB, Express, Angular, and Node.js. Algorithms and Data Structures

LCR Dice Game

The LCR Dice Game is a C++ console application that simulates the Left Center Right dice game for three or more players.

The enhanced application adds tournament play, persistent player statistics, leaderboard sorting, structured game results, modular gameplay functions, and stronger input validation.

View Repository Enhancement Narrative

Algorithms and Data Structures Enhancement Narrative

Artifact Description

The Left Center Right (LCR) Dice Game is a console-based C++ implementation of the multiplayer dice game. It supports three or more players who take turns rolling dice and transferring chips until only one player has chips remaining.

The original application demonstrates object-oriented programming through separate Player and Dice classes while using vectors, loops, conditional logic, random number generation, and file input to manage gameplay. Although the original version worked as a single-game simulation, it did not preserve information across multiple games or provide a way to analyze player performance over time.

Justification for Inclusion

I selected this artifact because it provided a strong opportunity to demonstrate the practical use of algorithms and data structures while building on an existing object-oriented application.

The original program already used vectors and class-based design, which gave me a useful foundation for expanding the application rather than simply correcting existing code. The enhancement required me to evaluate limitations in the original design, choose appropriate data structures for new functionality, and implement algorithms that improved both functionality and organization.

The largest enhancement was the addition of tournament mode. Players can now complete multiple games during one execution of the program while cumulative statistics are maintained throughout the tournament.

This required restructuring the original program so that gameplay could be executed repeatedly without losing tournament information. I separated major responsibilities into reusable functions, allowing the game logic, statistics processing, and leaderboard generation to operate independently. This improved readability, maintainability, and future extensibility.

Data Structures and Algorithms

To manage tournament statistics efficiently, I introduced an unordered_map containing a custom PlayerStats structure for each player.

Each player's record tracks:

  • Games played
  • Tournament wins
  • Total chips won

An unordered_map was appropriate because player names can be used as keys, providing efficient average constant-time lookup and update operations. This is more suitable for maintaining player statistics than repeatedly searching through a vector as tournament data grows.

This enhancement helped demonstrate the importance of selecting a data structure based on the needs of the problem rather than using the same container for every type of information.

Another major enhancement was the tournament leaderboard. Statistics stored in the map are copied into a vector and sorted using the C++ Standard Library std::sort algorithm with a custom lambda comparator.

Players are ranked using three conditions:

  1. Total wins in descending order
  2. Total chips won in descending order
  3. Player name alphabetically when a tie remains

This combines multiple data structures with a sorting algorithm to transform stored statistics into useful information for the player.

Reliability and Input Validation

I also strengthened the reliability of the application by improving input validation.

The program safely rejects invalid player-count input before gameplay begins and only accepts whole-number values representing at least three players. This prevents malformed or unsupported input from disrupting the game.

Although this was a smaller change than the tournament functionality, it improved the overall robustness of the application and reinforced the importance of defensive programming.

Skills and Course Outcomes

This enhancement demonstrates algorithmic problem solving, data structure selection, object-oriented programming, modular design, input validation, and use of the C++ Standard Library.

It demonstrates my ability to evaluate a limitation in an existing application and design a solution using appropriate algorithms and data structures. The use of an unordered_map for efficient statistics management and a vector with std::sort for leaderboard generation reflects deliberate choices based on the responsibilities of each structure.

The enhancement also demonstrates professional technical communication through documentation, code review, and explanation of design choices and trade-offs.

Finally, the project demonstrates the use of C++, object-oriented programming, Standard Template Library containers and algorithms, testing, modular development, and GitHub version control to create a substantially expanded software solution.

Reflection

Working through this enhancement reinforced the importance of selecting the right data structure for a specific problem rather than forcing every feature into the same implementation.

The original program only required a vector because its data existed for the duration of a single game. Once tournament functionality was introduced, player statistics needed to persist across multiple games and be updated repeatedly. An unordered_map provided a much better solution for that responsibility.

I also gained more experience using Standard Template Library algorithms, particularly std::sort with a custom comparator, to organize more complex data. Building the leaderboard showed how algorithms can turn stored information into meaningful output rather than simply manipulating values internally.

Refactoring the gameplay into reusable functions was another important part of the enhancement. Separating gameplay, statistics updates, and leaderboard generation made the application easier to understand and test while also making future changes easier to implement.

One of the most valuable lessons from this project was seeing how a series of focused architectural changes can significantly expand an existing application. I did not need to rewrite the game from the beginning. Instead, I was able to preserve the working original design and extend it through reusable functions, additional data structures, and sorting logic.

The result transformed a single-game simulation into a tournament application while demonstrating growth in algorithmic thinking, data structure selection, software organization, and problem solving.

Travlr Getaways Database Enhancement

The database enhancement expands the MongoDB and Mongoose implementation used by Travlr Getaways.

Improvements include stronger schema validation, database indexes, MongoDB aggregation reporting, REST API integration, and an Angular Trip Report interface displaying database-generated statistics.

View Repository Enhancement Narrative

Database Enhancement Narrative

Artifact Description

Travlr Getaways is a full-stack MEAN application that uses MongoDB for data storage, Express and Node.js for the server and REST API, and Angular for the administrative interface.

The application stores information about available travel packages and allows authenticated administrators to add, view, edit, and delete trip information.

I selected Travlr Getaways for this database enhancement because the application already contained a functional connection between MongoDB and the rest of the application. This provided a strong foundation for demonstrating more advanced database skills.

The original application primarily used MongoDB to support CRUD operations. For this enhancement, I expanded the role of the database by strengthening data validation and using MongoDB aggregation to transform stored trip data into useful administrative information.

Justification for Inclusion

I selected this artifact because it demonstrates how database development fits into a complete software system rather than existing as an isolated component.

The application connects MongoDB to a Mongoose data model, Express controllers and routes, a REST API, and an Angular administrative interface. This demonstrates my ability to work with data across multiple layers of a full-stack application.

One major part of the enhancement involved strengthening the Mongoose trip schema. I added validation rules and constraints to the fields used by trip documents. These changes help prevent invalid or incomplete information from reaching the database and improve the consistency of stored records.

I tested the validation rules by attempting to submit values that did not meet the established requirements and confirmed that invalid information was rejected with appropriate error handling.

MongoDB Aggregation and Reporting

I also created a database-driven reporting feature using the MongoDB Aggregation Framework.

The aggregation pipeline processes the trip collection to calculate:

  • Total number of trips
  • Average trip price
  • Average trip duration

Because some values in the original application were stored as formatted strings, the pipeline performs string processing and data conversion before calculating the statistics.

A second aggregation groups trips by resort and counts the number of trips associated with each resort.

The aggregation results are exposed through a new Express API endpoint. I then integrated this endpoint into the Angular administrative application through the trip data service and created a Trip Report interface.

The report presents the total number of trips, average price, average duration, and trips grouped by resort in a readable administrative dashboard. Navigation was also added between the main trip listing and the report.

This enhancement demonstrates a complete flow from stored MongoDB data, through server-side processing and a REST API, to information presented to the end user.

Skills and Course Outcomes

This enhancement demonstrates the use of modern database and full-stack development techniques to create functionality that provides practical value to users.

The strongest alignment is with the outcome involving the use of well-founded computing techniques and tools to implement solutions that deliver value. MongoDB, Mongoose, Express, Node.js, and Angular work together to create a reporting feature that provides administrators with useful information about available trip data.

The enhancement also demonstrates computing-solution design through the aggregation pipeline. The pipeline required multiple processing stages, including data conversion, grouping, averaging, sorting, and projection. I had to evaluate how the original data was represented and determine how it needed to be transformed before calculations could be performed.

A security-focused development mindset is also demonstrated through stronger schema validation and controlled administrative access. Improved validation helps protect data integrity by limiting the types of values that can enter the database, while JWT authentication continues to protect administrative operations.

The Trip Report also demonstrates professional communication by presenting database-generated information in a clear and usable format for an administrative user rather than exposing only raw API output.

Reflection

Enhancing Travlr Getaways helped me better understand the role a database can play within a full-stack application.

In the original project, I primarily viewed MongoDB as the location where the application stored and retrieved trip records. Through this enhancement, I learned how the database can also perform meaningful processing and generate information that supports application features.

One of the most valuable parts of the enhancement was working with MongoDB aggregation. I learned how multiple stages of an aggregation pipeline can work together to transform documents into useful results. The pipeline converts formatted price and duration values into numeric data, calculates averages, groups documents, sorts results, and controls the final output.

This showed me that processing data directly within the database can sometimes be more appropriate than retrieving every document and performing all calculations in the application layer.

One challenge involved the structure of the original data. Values such as price and trip duration were designed primarily for display and stored as formatted strings. This made calculating averages more complicated because the aggregation pipeline first had to extract or convert numeric values.

Working through this issue helped me recognize an important database design trade-off. A structure that is convenient for presentation is not always ideal for querying and analysis. If I were designing the database again from the beginning, I would consider storing numeric price and duration values separately from their formatted display values.

I also encountered challenges while connecting the aggregation functionality to the Express routing and controller system. Problems involving route ordering, controller exports, and aggregation syntax required me to trace requests through several layers of the application.

Resolving those issues strengthened my understanding of how the Angular client, Express API, Mongoose model, and MongoDB database communicate.

Finally, creating the Angular Trip Report reinforced the idea that database functionality should ultimately provide value to the user. Rather than leaving the aggregation results as raw JSON from an API endpoint, I integrated the results into the administrative interface.

Seeing statistics generated in MongoDB and displayed in the application connected the database concepts to the larger purpose of the software.

Overall, this enhancement significantly improved the original Travlr Getaways application. It now demonstrates stronger database validation, data integrity, aggregation and reporting, REST API integration, and full-stack communication.

More importantly, the enhancement reflects my growth from thinking of a database as simply a place to store application data to understanding how databases can validate, process, analyze, and communicate information effectively.
